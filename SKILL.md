# Local business revamp

Run user-sized business batches for Albert: discover → visually qualify → collect contact details → generate from the selected template → verify → host → contact. Batches default to five websites and may request 1–100; process larger batches in worker waves. Use the fast Codex in-app browser (`iab`) through `mcp__cua_repl`, not a ChatGPT conversation or native shared desktop navigation. If a worker browser is unavailable, leave the job with the coordinator for that browser step; never invent observations or turn that recoverable condition into a terminal job block.

The skill folder is the application root. Resolve it from this SKILL.md, set it as the working directory, and read `settings.json`. Relative paths below resolve here. `data/` holds the durable cross-run ledger; `runs/` holds per-business artifacts. Never use a temporary DB during a real batch. Generation requires Python 3 and a prepared template. Node/npm are needed only for template edits; public deployment requires Vercel login. Firecrawl is the default homepage/contact-page screening path; see [Firecrawl scouting](references/firecrawl-scouting.md). Keep credentials out of messages, files destined for hosting and dashboard events.

For state-wide batches, the coordinator discovers the city list and dispatches one fresh scout per city sequentially, feeding fresh builder/sender agents, sharing one completed-outreach target and cross-city deduplication. A supplied state is sufficient; do not require a city list from Albert. For new batch runs, use the [parallel scouting and building skill](skills/local-business-revamp-parallel/SKILL.md) as the default coordinator workflow. It shares this application, ledger, template and fixed outreach reference; it does not create a second dashboard. The workflow below remains the single-worker fallback.

## AI owns the complete run

When Albert runs this skill with an industry and city, carry each qualified prospect through **research → choose template and color → run generator → verify → deploy → verify public URL → submit outreach → record result**. The AI does this work; do not ask Albert to enter a business name, phone, email, address or theme color, fill out a dashboard form, run a command, deploy a site, or manually send the prepared message. For a real batch, submit outreach when the original form is usable; otherwise the required final step is a verified website and manual outreach handoff under [Manual outreach](references/manual-outreach.md); honor only an explicit dry-run or narrower scope. If the active computer-use environment imposes a non-overridable confirmation at the final form action, request it then and only then.

The dashboard is a contact sheet for batch requests, live progress, generated previews and outcomes. It has no per-business setup form or theme picker. Ask only for missing run-level inputs (industry/city), or a real blocker the AI cannot resolve, such as unavailable account access. An instruction to update this skill changes the workflow; it does not launch a prospecting batch.

## Keep the batch advancing

- Keep a coordinator loop active: discover and qualify candidates, allocate available worker capacity, perform coordinator-owned browser steps, collect results, and refill the next wave. After a skip, continue discovery immediately. After a worker finishes, assign the next available job. When all useful work depends on active workers, wait for their results and then continue.
- Send progress reports in commentary and keep working. A status question such as “Are you running anything currently?” calls for a truthful brief answer followed by continued execution; it does not cancel or pause the batch.
- End the run only when the requested scope is processed, discovery is exhausted with recorded search coverage and a reported shortfall, Albert explicitly stops it, or a concrete blocker prevents all remaining authorized work. A blocker affecting one prospect does not stop independent work. Prepare any genuinely required approval at the actual action, and continue other authorized work while it is pending.
- Before ending, check the requested count, discovery coverage, unfinished jobs, and actual worker/process state. A dashboard server, ledger `running` flag, retained browser tab, or scheduled future wakeup is not evidence of active batch processing. State what is executing now and what is waiting; never promise continued background work without a verified execution mechanism.
- A recurring heartbeat is not a substitute for this coordinator loop. Do not create one merely to recover from ending a turn prematurely. Use scheduling only when Albert requests later or recurring execution, following the available automation tool's rules.

## Discover, qualify and allocate

Read [coordination.md](references/coordination.md). Use Google web search in `iab` as the discovery source, not Google Maps. Begin on Google results page 10 (the `start=90` results offset or equivalent pagination) and continue through later pages; do not fall back to pages 1–9 unless Albert asks. Search the requested industry and city, then open each business's actual website to confirm its name, city/service area and ownership. Work in bounded waves of up to four candidates per requested website, replacing unsuccessful prospects until the requested completed-outreach count is reached or the search is exhausted. Skip directory-only listings, duplicates, already contacted or opted-out businesses, dead websites, browser-verification or invalid-certificate blockers, and visually strong sites. Do not use copyright years, publication dates, domain age, or other time-based signals to qualify or reject a prospect.

Qualify solely by **observed visual weakness**, e.g. dense fixed-width layouts, illegible typography, tiny navigation, stretched/low-resolution imagery, poor contrast, broken/placeholder content, confusing service hierarchy, or a visibly broken mobile layout. The site may be newly published; age is irrelevant. Save desktop/mobile observations and at least two concrete findings, for internal qualification evidence; do not insert them into outreach. Never say “not responsive” without actually checking a narrow viewport. Preserve evidence URLs and screenshots. If the available browser cannot inspect mobile, record that limit and use verified desktop issues instead.

Before qualifying a prospect for a build, screen its original contact page via Firecrawl (browser fallback for ambiguous evidence) and confirm an actual form suitable for a website proposal exists, with a message field and submit control. A contact link, email address, phone number, newsletter signup or customer-review form does not satisfy this check. Record the verified form URL as `contact_url` and save the observed fields and submit control in the qualification evidence. Check for visible CAPTCHA, opt-out notices and required commitments using [outreach.md](references/outreach.md). If no usable form is found but the business qualifies, still generate, deploy and verify the preview, then follow [Manual outreach](references/manual-outreach.md) with the prepared message and verified contact details. Recheck the saved form immediately before filling and sending; do not assume it remains usable.

The coordinator alone registers candidates and aliases in the shared ledger, then delegates independent business jobs. For a requested batch count (for example 50), keep discovering and registering qualified prospects until the target count of `complete`/`sent` jobs is reached; skipped, blocked and uncertain jobs require fresh replacements, while processing builds in capacity-limited worker waves. Canonical domain plus verified alternate domains, normalized phone and email identify duplicates across batches. Compare names/addresses too; domains alone do not identify every business. Treat normal recoverable workflow gaps as work to resolve rather than terminal job blocks: the coordinator owns unavailable worker-browser steps, and publicly listed business address details are collected from the original site or Google results before form completion. Before a worker claims a browser-dependent job, confirm that its private `iab` browser surface is available. If a worker lacks an `iab` surface, do not claim or block the job for that reason: the coordinator retains browser ownership and performs the required original-site inspection, public-preview verification, and contact-form interaction, while delegating only non-browser work that can be completed safely. Up to five workers are desired; use `min(5, available worker slots)`, reserving the coordinator's slot. With four total slots this means three workers and larger batches proceed in waves. Read the worker model and reasoning effort from `settings.json` and pass those exact settings when spawning workers. Do not spawn nested workers or create user-facing Codex tasks. Show actual capacity. Keep coordinator-owned browser tabs available for Albert to watch, following coordination.md.

## Build and verify — quick template mode

The default is volume production from a prepared English industry template. Start with `electrician`; do not custom-write every prospect’s website, scrape galleries, search for stock photos per business, or clone the old Delivery template. The reusable base design and stock imagery live in `templates/electrician/`. The AI invokes the generator command directly. The dashboard’s **Queue batch** form only queues discovery/outreach work for Codex; generated previews and job progress appear automatically.

Read [production.md](references/production.md) for the quick command and preparation rules. Collect the business name, public phone/email and publicly listed address from its actual website; use a trusted search result only to fill a missing detail and record the source. At least one verified contact method is required; omit unavailable optional fields rather than inventing them. Choose the template from the business’s industry. Choose `theme_color` yourself: use its identifiable logo or dominant brand color as a six-digit hex value; if branding is unclear, choose a suitable industry color (default electrician blue `#2563eb`). Honor a user-specified color if supplied, but never ask the user to choose one. Record the chosen color and its source or fallback rationale with the business facts. Keep the template’s neutral English copy and bundled stock photography. No invented hours, reviews, certifications, prices, availability or completed projects. Confirm the electrician template is appropriate for the prospect. For other industries, select a suitable available template; do not silently use electrical copy for a different trade.

Run the command yourself with the collected values; this example shows its syntax: `./website --theme-color "#2563eb" --name "Business Name" --phone "+44 20 7946 0958" --email "hello@business.com"`. Pass `--theme-color "#2563eb"` (or `theme_color` in JSON) to apply the selected business color everywhere. Only these configuration values change per business: `name`, `phone`, `email`, `street`, `city`, `zip`, `theme_color`. Keep the generic text, services, images and layout unchanged. The output gives a unique folder under `runs/quick/` with a deployable `site/`. Record that folder in the job ledger. No dependency installation, rebuild, image search or full content rewrite is needed per business. Run the full template QA only when editing the master; for a generated copy check the name, contact links and successful rendering, then verify the public URL after deployment. The setup target is about 30 seconds; discovery, public deployment and outreach are separate and must not be represented as instantaneous.

Use the shared cached Firecrawl homepage/contact-page evidence for form screening, visual screenshot assessment and contact facts. Use live original-site inspection only for ambiguous evidence and the final sending check. Do not repeat Firecrawl credit checks or scrape pages whose screening evidence is already sufficient. Keep the existing ledger and duplicate/outreach safeguards.
